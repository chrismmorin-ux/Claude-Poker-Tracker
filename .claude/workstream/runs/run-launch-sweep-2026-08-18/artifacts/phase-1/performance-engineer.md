### PERFORMANCE ENGINEER

#### Key Concerns (top 3-5)

1. **The live-advisor hot path blocks the main thread for its FULL evaluation, with zero opportunity to paint, on every postflop decision -- CRITICAL.**
   `src/utils/liveAdvisor/computeHelpers.js:251-272` (`buildPostflopAdvice`) calls `evaluateGameTree({...})` WITHOUT passing `onFastResult`. I grepped every production call site (`src/hooks`, `src/utils/liveAdvisor`) and `onFastResult` appears in exactly one place outside engine internals/tests: its own declaration and consumer-guard in `src/utils/exploitEngine/gameTreeEvaluator.js:954,1611-1622`. The yield-to-host macrotask (`gameTreeEvaluator.js:1611-1622`, "THE YIELD IS LOAD-BEARING") only fires `if (onFastResult)`. With no production caller wiring it, that branch never executes on the live path, so the documented two-phase design (SYSTEM_MODEL.md Section 2.3, `evaluateGameTree`'s own CLAUDE.md doc) is not what actually runs. `useLiveActionAdvisor.js:206` does `result = await buildPostflopAdvice(...)` synchronously on the render thread with no worker, no yield, no fast paint -- the phase-1 depth-1 answer, the phase-2 refinement (`refinementBudgetMs` default 2000ms), and every synchronous sub-stage between them run as one uninterrupted block. SYSTEM_MODEL.md Section 7.1 records full refinement measured up to 26s on a wet flop, on desktop. This is confirmed, not inferred -- it is the same gap WS-468 exists to close ("onFastResult has zero production callers"), and I independently verified it by reading the call site rather than trusting the ticket text.

2. **Wall-clock advice latency on the target device has never been measured, and the finding tracking it (FIND-109) is still open -- HIGH, launch-blocking for the live-table use case.**
   `.claude/workstream/findings/FIND-109.yaml:5` -- `status: open`. `.claude/workstream/queue/WS-468.yaml:5-6` -- `status: backlog`, `claimed_by: null`, `started_at: null`. Its accept criteria (line 30-31) require "a session summary... shows p50/p90/max advice latency on the founder's phone... over n>=50 postflop decisions" -- nothing in the repo produces this today: `grep -r "treeMetadata.latency"` across `src/` returns matches ONLY in test files (`gameTreeEvaluator.test.js`, `stageLedgerOutcome.test.js`, `refinementDeterminism.test.js`, `depthReachability.test.js`) and the engine's own CLAUDE.md -- zero production persistence sites. `refinementBudgetMs = 2000` (default, `gameTreeEvaluator.js`) was chosen on desktop per SYSTEM_MODEL.md Section 7.1 and A-07 ("Game tree eval < 100ms on target device... RT-7 (physical device profiling) will validate") -- RT-7 never ran. Combined with finding #1, the founder's phone has never once had its actual advice latency measured while sitting at a table, and the mechanism that would let a slow evaluation paint something usable in the meantime is unwired. This is the single highest-impact gap for the app's actual use case (live 9-handed play).

3. **The full per-player analysis pipeline -- including the 169-cell Bayesian range update and exploit generation -- runs synchronously on the main thread once per changed player, after every hand save, with no Worker offload.**
   `src/hooks/usePlayerTendencies.js:99-168`: `Promise.all(changedPlayers.map(async (player) => { ... const result = runAnalysisPipeline(player.playerId, hands, userId, cachedRangeProfile, sessions); ... }))`. `runAnalysisPipeline` (`src/utils/analysisPipeline.js:63`) is a plain synchronous function, not `async` -- no `await` inside it. It runs all 8 steps (`buildPlayerStats` -> `buildRangeProfile` (Bayesian updater over the 169-cell grid) -> `buildPositionStats` -> `generateExploits` -> `buildBriefings` -> `accumulateDecisions` -> `detectWeaknesses` -> `buildVillainDecisionModel`/`buildVillainProfile`/`inferVillainThoughts`) synchronously per changed player, CPU-bound, on the thread that also owns rendering. `Promise.all` around an array of `async` functions containing no internal `await` before the sync call does NOT parallelize this work off-thread -- it still executes each player's pipeline back-to-back on the JS main thread. This fires after every hand in a live session (the effect is keyed on hand-count change), i.e. mid-session, competing directly with the founder recording the next hand's actions. SYSTEM_MODEL.md Section 7.2 documents the MC-fallback and per-player-recompute cost generically but does not name this as blocking; I confirmed the blocking nature by reading the call chain directly.

4. **Bundle: the eager/critical-path payload is ~1.25 MB raw / ~398 KB gzip before first paint -- measured, not estimated.**
   `npm run build` (this session) output + `dist/index.html`:
   - `<script type="module" src="/assets/index-CSjMXJ_6.js">` -- 782.0 kB raw / 243.3 kB gzip (eager `<script>`)
   - `<link rel="modulepreload" href="/assets/exploitEngine-C0Xp7SAn.js">` -- 357.7 kB raw / 121.8 kB gzip
   - `<link rel="modulepreload" href="/assets/firebase-CLRefKio.js">` -- 109.5 kB raw / 33.2 kB gzip
   - `<link rel="stylesheet" href="/assets/index-BRB87q18.css">` -- 83.6 kB raw / 14.3 kB gzip

   Total critical path: 1332 KB raw / ~412 KB gzip, all fetched (script + two modulepreloads + stylesheet) before the app can render anything, on every cold load. `vite.config.js:85-94` -- `manualChunks` splits only `firebase` and `exploitEngine`; there is no vendor chunk for React/ReactDOM, no split for `pokerCore`/`rangeEngine`/`persistence`/reducers/contexts/hooks, which is why the main entry chunk alone is 782 KB raw. Rollup's own build warning flags this ("Some chunks are larger than 500 kB after minification"). `.claude/rules/performance-baseline.md` sets a 3s page-load budget; on typical casino cellular/WiFi (1-5 Mbps effective, first visit with no service-worker cache -- the PWA precache only helps on repeat visits), transferring + parsing/compiling ~1.3 MB of JS is a real risk against that budget, and it has never been measured against the S22 specifically (same FIND-109 gap: no device-specific measurement exists for load time either, only a generic rule).

For the primary use case (guest, at-the-table, IndexedDB-only), this is 33 KB gzip / meaningful parse/init cost paid unconditionally for a capability (cloud sync) most sessions never invoke.

#### Hidden Risks

- **The 26s worst-case refinement (SYSTEM_MODEL.md Section 7.1) is a real value the live path can hit today**, not a theoretical one, because nothing bounds it on the live path -- WS-468 step (4), the "production-only Promise.race wall-clock deadline," is unbuilt (`status: backlog`). A wet-flop decision at the table could freeze input recording for tens of seconds with no fallback; the founder would be staring at a frozen UI mid-hand, which is the worst possible failure mode for a live-play tool.
- **`Promise.all(changedPlayers.map(...))` in `usePlayerTendencies.js` scales with the number of players who acted in a hand, not with a fixed cost.** At 9-handed, a hand where most seats acted (a raised, multi-way pot -- common) can trigger the full 8-step pipeline for 6-8 players in one synchronous burst, immediately after the founder finishes recording the hand and likely while they're also trying to record the next hand's blinds/antes.
- **The `getRangeProfile` reads inside that same map (`usePlayerTendencies.js:104`) and the `saveRangeProfile`/`updatePlayer` writes (lines 117, 136) are one transaction each, per changed player**, not batched into a single transaction. Per IndexedDB batching doctrine (batch writes, avoid per-item transaction overhead), this is proportionate at 9 players/session but is the closest thing in the codebase to the N+1 pattern the brief asked me to check for -- it is real, just currently small-N. It will not stay small-N for free if `usePlayerTendencies` is ever reused for a multi-table or replay-many-sessions view.
- **No `navigator.storage.estimate()` call anywhere in `src/`** (grep confirmed zero matches) despite TD-20 in SYSTEM_MODEL.md Section 11 rating this HIGH for exactly the device class in question ("mobile Safari ~50MB"; Android Chrome has its own quota cap). A-06 in SYSTEM_MODEL.md Section 9.3 ("IndexedDB quota... is sufficient") is an unvalidated assumption with no monitoring -- a founder who fills quota mid-session (blob writers, growing range-profile store) gets an unhandled write failure with no warning, at the table.
- **The equity Worker exists (`assets/equityWorker-DiqnskEX.js`, 9.1 KB) but SYSTEM_MODEL.md TD-08 records the preflop MC path bypassing it** ("`handVsRange` called directly in `preflopAdvisor`"), with RT-31 listed as the mitigation. I did not independently re-verify RT-31's completion in code this session (out of the grounded-evidence budget I had); if it is still open, the single most frequent computation (preflop, every hand) is main-thread MC on top of everything above. This should be independently re-verified before launch, not assumed fixed because a table cell says "mitigation."

#### Likely Missing Elements

- **No production telemetry for `treeMetadata.latency`** -- the value the engine already computes at every evaluation is discarded (confirmed by grep: only test files reference it). Without this, "is the phone fast enough" is not just unmeasured, it is unmeasurable from the field -- there is no instrument to turn on.
- **No macrotask yield on the live path** (finding #1) -- the mechanism to make phase-1/phase-2 actually two-phase in production is built and tested (`gameTreeEvaluator.js`) but not wired to its one real caller.
- **No wall-clock deadline / cancellation** for in-flight evaluations superseded by a newer action (WS-468 step 5, unbuilt) -- combined with no yield, a stale, slow-in-flight evaluation cannot even be abandoned when the founder moves on to the next street.
- **No bundle-size regression gate.** Nothing I found in `vite.config.js` or the referenced test runner fails a build on chunk-size growth; Rollup's warning is advisory-only. There is no visible `rollup-plugin-visualizer` step for routine bundle inspection.
- **No React vendor chunk / deeper manualChunks split** beyond firebase + exploitEngine -- pokerCore, rangeEngine, persistence, and the 20 contexts/62 hooks all ride in the single 782 KB entry chunk.
- **No device-specific measurement of ANYTHING performance-related on the S22** -- not advice latency (FIND-109/WS-468), not page load, not IndexedDB transaction latency, not GC pause behavior under the render load SYSTEM_MODEL.md Section 7.2 already flags (React.memo gap was resolved per TD-10, but even that resolution's real-device effect is unmeasured).

#### Dangerous Assumptions

- **"It works on my desktop dev server, so it will feel fine on the S22."** The S22 is a capable chip, but it is still running this under a CSS `transform: scale(~0.695)` canvas, likely on battery-saver-throttled Chrome, at a felt table where a multi-second freeze reads as "the app is broken," not "the refinement stage is thorough." Nothing in the repo has tested this distinction.
- **"The two-phase design (WS-334) already fixed the blocking-UI problem."** SYSTEM_MODEL.md Section 2.3 describes the architecture in the present tense as though it is live behavior. It is live capability in `gameTreeEvaluator.js`, but finding #1 shows the one production caller does not invoke it -- the documentation and the shipped behavior have diverged, and a reader of SYSTEM_MODEL.md alone would conclude the blocking problem is solved when it is not.
- **"Code splitting exists because dynamic-imported views produce many small chunks."** True at the view level (StatsView, PlayerFinderView, PreflopDrillsView, etc. are all separate chunks -- genuinely good), but false at the level that matters for first paint: the shell that loads before any view can render is 782 KB raw / 243 KB gzip by itself, plus two modulepreloaded chunks. Per-view splitting does not help time-to-interactive on first load.
- **"Guest mode has no Firebase cost since credentials aren't required."** Credentials aren't required, but the Firebase SDK bundle is still fetched and preloaded regardless of whether the founder ever signs in this session.

For the advisor specifically, the aggregate's NOT READY and my own lens's assessment agree, for different and independently-verified reasons. Any "shippable subset" claim must exclude live in-hand advice until WS-468 lands.
