#### Hidden Risks

- The suites actual size vastly exceeds the documented figure, in the direction that hides risk rather than exaggerates it. CLAUDE.md claims "~5,400+ tests across ~184 test files." Measured via `npx vitest run` (full run, no gate bypass tricks): 686 test files, 15,922 tests (15,898 passed, 2 failed, 22 skipped), 549s wall time. The suite is about 3x the documented size and about 9 minutes long. A founder trusting the documented number would badly underestimate both the coverage the suite provides and the time cost of running it, and would have no reason to suspect the smart-test-runner gate could be silently skipping over 15,000 tests behind a governance check unrelated to product code (see Concern 2).
- One test alone takes 8 minutes. `src/utils/drillContent/__tests__/shapesCatalog.test.js` -- "every (hero, villain) pair passes its canonical lane band" -- measured at 480,651ms (480.65s) in the full run. This single test is 87% of the entire suites wall-clock time. It is tagged `slow-unit` (visible in output), so its cost is at least labeled, but there is no visible budget/threshold enforcement -- a regression that made it 2x slower would not fail CI, it would just make every local run 16 minutes instead of 9.
- A legitimate test times out under full-suite parallel load but passes standalone. `src/components/views/PlayerFinderView/__tests__/PlayerFinderView.smoke.test.jsx` failed with `Test timed out in 10000ms` in the full run, then passed in 2.3s when run in isolation. This is a flake caused by worker contention under the 549s/15,922-test load, not a product defect -- but it means the suites own weight produces false-negative test signal at CI-relevant scale, and nobody has raised the timeout or isolated this test.
- The build succeeds but the main JS chunk is 782 kB minified (243 kB gzip) (`dist/assets/index-6jypFfmm.js`), triggering Vites ">500kB chunk" warning. This ships to a Galaxy S22, possibly on mobile data at a poker table. The warning is emitted but nothing in CI fails on it or tracks it -- an instance of build warnings treated as noise.
- Machine-affinity risk for this exact sweep: per `.claude/rules/machine-affinity.md`, UI/`.jsx` work is `g16`-labeled, but the villain-archetype commits (`scripts/backtest/`, `scripts/villainArchetype/`) are `node1`-shaped batch work that landed directly on local main without ever going through CI (see Concern 1). The doctrine anticipates this class of work being long, unattended, and checked back on -- but nothing enforces "checked back on" translating into "pushed and CI-validated" before the next commit stacks on top.

#### Dangerous Assumptions

- "CI is green" is being treated as a live signal when it is a 2-day-stale one. The last CI run predates 8 local commits, one of which is independently confirmed broken. Anyone reasoning "CI passed, so main is fine" right now is reasoning from a run that never saw the code currently on disk.
- "Tests pass" claims embedded in commit messages are being trusted without a corresponding CI run to back them. Commit `56ef59096`s message states "4,887 tests pass" -- plausible for whatever subset the author ran, but it did not include, or did not correctly evaluate, the golden-case assertion that fails today. A commit-message test-count claim is not a substitute for a CI status.
- The label-ledger and additive-schema gates are assumed to be narrowly scoped checks that "just" block commits when something needs a decision. In practice the label-ledger gate is currently blocking 100% of test signal via `smart-test-runner.sh`, for a reason (unledgered constants in a new backtest module) that has nothing to do with product correctness. A gate whose failure mode is "no information" rather than "specific information" trains whoever hits it to bypass it (as this session did, via `npx vitest run` directly) rather than fix the ledger -- which defeats the gates purpose over time.
- The architecture quick-ref numbers in CLAUDE.md are assumed current enough to orient a session. They are read at the start of every Standard Mode and Strategic Mode session per the CWOS protocol. Being off by 2-3x on hook/context/view counts is exactly the kind of silent drift that degrades every downstream judgment call about whether a file is oversized or a hook is doing too much -- the numbers this reports own lens depends on to calibrate severity are themselves wrong in the source-of-truth doc.
