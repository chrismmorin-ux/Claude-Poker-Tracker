Per `system/decisions.md:834` (DEC-036): *"Every existing caller silently upgraded from a depth-1 answer to a refined one, because they already `await` the return value."* Net effect on the live table: the founder now waits up to ~2.4s (context build + refinement budget) for every postflop decision where he previously got an answer near-instantly (because depth-2/3 never ran at all before WS-334). This is a straight latency regression on the 15-30s live decision window, introduced by a fix and never surfaced to the UI layer. `LiveAdviceBar.jsx` (git-touched once in the whole window, `0457b9a3`, for an unrelated label string) has no loading/refining state distinct from its existing `isComputing` spinner — the founder cannot tell "fast answer, more coming" from "just slow."

But because no production caller passes `onFastResult`, there is no "withholding" happening — every live postflop `await evaluateGameTree(...)` already returns the refined (depth-2/3, when reached) result today. WS-361 records two known-wrong-looking depth-2 outputs (OESD call priced −26.2 EV; AA-on-A72 preferring check over bet) and states plainly: *"Depth-2's EV outputs have never been validated in production"* (`exploitEngine/CLAUDE.md:671`). #### Dangerous Assumptions

- **DEC-036 / AS-2 assumes** *"the founder acts on the fast answer and treats the refined one as confirmation"* — but the fast answer is never delivered to any production consumer, so this assumption cannot currently be tested by the mechanism the decision record itself proposes. The assumption is carried forward unfalsified while the actual shipped behavior (silent full wait) is the one AS-2 was written to avoid.
- **WS-334's own trade-off section assumes the two-phase change is inert on the live surface until "Phase C" design work wires it** (`decisions.md:834`: *"The refined answer reaches no screen yet… Wiring the second phase is Phase C and is design-gated"*) — this is **false as currently shipped**: because `useLiveActionAdvisor` already awaits the full refined result by default parameter behavior, the refined (and per WS-361, unvalidated) answer already reaches the screen; only the *fast* intermediate answer is unwired. The design gate that's supposed to control this rollout is protecting the wrong half of the feature.
