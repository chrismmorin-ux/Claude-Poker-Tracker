This is a correctness-relevant finding, not just a latency one, because the tool's premise is real-time table decision support: an answer that arrives after hero has already acted is not a degraded answer, it is a wrong one (arrives too late to inform the decision it was computed for).

#### Likely Missing Elements

- **No mobile-device calibration path exists at all.** `scripts/backtest/calibrate-refinement-units.mjs` is a Node script that runs the offline `dumpGameTreeEV` battery — it cannot run in a mobile browser, and nothing in the shipped bundle detects device class and selects among multiple calibrated constant sets (or falls back to a conservative wall-clock circuit-breaker when device speed is unknown).
- **No wall-clock safety net alongside the logical clock.** The WS-432 rationale correctly rejects wall-clock-only gating for *reproducibility* reasons (a Result Card must be deterministic), but that argument governs the *offline backtest* consumer of this code, not the *live app* consumer — the same module serves both (`refinementWork.js:20-24`, "this module sits inside the engine's 37-module worker closure... and is also read by the replication stamp"), and the live path inherited the backtest's requirement (pure logical gating) without also getting a production-only outer bound (e.g., `Promise.race` against a hard wall-clock timeout that returns the depth-1 answer if refinement overruns). That combination is available without touching determinism for the backtest: the live caller could wrap the awaited `evaluateGameTree()` in a real-time deadline and fall back to the fast answer.
- **No telemetry from the live app reporting actual `totalMs` distributions off desktop.** `treeMetadata.latency` already carries `computeMs`/`totalMs` per evaluation (`gameTreeEvaluator.js:1430`) — the data needed to close this gap is already being computed and thrown away; nothing persists or aggregates it from real sessions.
- **Profiling on the actual reference device is absent from this session's changes.** WS-433/WS-432's acceptance criteria are entirely about determinism (bit-identical parallel vs. serial) and desktop wall-clock reduction (7-8x at 7 workers) — none of the acceptance criteria mention the Helio G80 or any mobile browser at all.

#### Dangerous Assumptions

- **"A budget of N ms buys the work a calibrated reference machine does in N ms — but deterministically, on every machine"** (`gameTreeEvaluator.js:993-994`, echoed in `refinementWork.js:39-42`) **is stated as fact and is an untested claim about every machine except the one it was measured on.** Determinism (same machine → same answer) is proven; device-portability of the *ms meaning* is not, and the doc that calibrates it is explicit that it only covers one desktop.
- **The assumption that replacing wall-clock gating with logical-unit gating is a pure win carries an implicit premise that real time no longer matters to the live consumer** — true for the backtest (which only cares about reproducible answers), false for the live advisor (which cares about a real 9-handed table's real decision window). The commit message frames this entirely as a correctness/reproducibility fix ("no depth-2/3 stage executed... while treeMetadata.depth reported 2" was the WS-334 bug this descends from) without re-examining whether the fix, applied identically to both consumers, re-introduces a *different* latency defect for the one consumer that was never unbounded before.
- **"2000ms" as a shipped default is treated as safe because it was safe under the old (buggy) wall-clock gate's intent** — but the old code's *bug* (spending the whole budget on context-building before any gate ran) was accidentally protective on slow hardware: it guaranteed refinement never ran at all, which is a fast (if useless) failure mode. The fix that makes refinement actually run — correctly, and this session's finding — removes that accidental protection on exactly the hardware class most likely to need it.
