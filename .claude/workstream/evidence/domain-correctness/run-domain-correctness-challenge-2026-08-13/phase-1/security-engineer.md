#### Key Concerns (top 5)

1. **A rake-honesty mechanism exists, is correctly designed, and is wired to nothing the founder can see.** `resolveRakeConfig` (`src/utils/rakeResolver.js:142-206`) is careful, purpose-built provenance: it returns `{ rakeConfig, tier, reason }` and deliberately distinguishes `tier: 'unknown'` ("rake NOT applied, and that is a gap, not a zero", line 166) from `tier: 'none'` (genuine zero-rake, e.g. tournament). `OnlineAnalysisContext.jsx:47-82` computes this and exposes it on the context value as `rake` specifically "so a surface can say WHICH rake the numbers were computed under" (line 78-80). But every consumer of that context destructures around it: `ExtensionPanel.jsx:67` (`tendencyMap, handCount, advice, isComputing`), `OnlineView.jsx:34` (same four), `CommandStrip.jsx:88` (`advice` only). None reads `.rake`, `.rake.tier`, or `.rake.reason`. `pushAdvice(advice)` (line 69) doesn't carry it to the extension side panel either. Net effect: when `venueClassOf`/`parseStakeLabel` can't identify the game (unparseable Ignition stakes label, missing captured blinds) the engine silently falls back to zero rake — exactly the multi-month defect `rakeResolver.js`'s own header documents as costing "+4.8pp of required equity live" — except now the *code path that was supposed to make that state visible* is itself dead. This is the shipped-but-inert pattern the project's own memory names (`feedback_shipped_but_inert_capability.md`), reproduced inside the very fix meant to close a version of it.

2. **`villainRequiredEquity` silently substitutes a plausible constant for missing/malformed pot geometry instead of erroring or flagging low confidence.** `src/utils/exploitEngine/foldEquityCalculator.js:378-400`: when `potSize`/`villainBet` fail `Number.isFinite(...) && ... > 0`, the raise branch returns a flat `1/3` (line 395); when `heroBetFraction` is non-finite or ≤0, the bet branch defaults to `0.75` (line 398). Call sites reproduce the same shape one level up — `gameTreeDepth2.js`'s `computePerComboEV`/`computePerComboCheckEV`/`computeRiverCheckEV` all compute `heroBetFraction: pot > 0 ? betSize / pot : 0.75` before calling in. This is a genuinely new surface as of WS-450 (`ed3dc3b6`): five previously-inline `betSize/(pot+betSize)` computations were centralized behind one seam, and centralizing them also centralized a silent default that none of them had named consistently before. A corrupted `pot` (0, negative, NaN — plausible from a mid-hand extension race, a stale `liveHandState` field, or a malformed imported hand) does not surface as an error or a `lowConfidence` flag; it produces a specific, confident EV number and top-line recommendation as if the geometry had been real. `requiredEquitySeam.test.js` (new in the same commit) pins the closed-form correct values but has **zero coverage of the fallback branch** — the untested path is precisely the one that fires on bad input.

None bumped `ENGINE_VERSION`. Every prediction the founder's own play has captured via `predictionAudit` — before today and after — carries the identical `modelVersion` string, so any PMC/calibration analysis that slices by model version cannot separate the systematically-double-priced-pot-odds era from the corrected one, or the flat-rake-on-fold-branches era from the per-branch one. #### Hidden Risks

This is presented in-code as intentional ("this panel serves the MANUAL live table, so the venue is live by construction"), but it means the sentinel value and the semantic check happen to line up by coincidence of string content, not by an explicit `source: 'live'` field — a future edit to `venueClassOf` or a future caller reusing this pattern for a non-live surface would silently misclassify venue class, which is exactly the transfer error (`rakeResolver.js:29-36`) the module exists to prevent.

#### Dangerous Assumptions

- That a `0.75` (bet) or `1/3` (raise) fallback in `villainRequiredEquity` is a safe, conservative default when geometry is missing. It is not visibly conservative or aggressive — it is simply *silent*: the caller cannot distinguish "the engine computed 0.75 because the bet really was pot-sized" from "the engine computed 0.75 because `potSize` was 0." Both produce an identically-confident recommendation.
- That exposing a provenance field on a context value (`rake` in `OnlineAnalysisContext`) constitutes "making the gap visible," per the module's own stated goal, when nothing renders it. Availability in a React context is not the same as reaching the founder.
- That `ENGINE_VERSION` co-versioning with `APP_VERSION` ("no separate semver," `runtimeVersions.js:12-14`) is harmless because the two are "co-versioned" — this assumption predates a period where the engine has now had at least three algorithm-shape changes (WS-436, WS-450, WS-451) in eleven days without the app's architecture version changing at all, so the co-versioning premise (engine and app change together) has already stopped holding in practice while the code still asserts it holds by construction.
- That a style label being "deliberately unread" by the decision model (`villainDecisionModel.js:742`) closes the loop on WS-436's refutation. It closes the loop for the *engine's* trust boundary; it does not close it for the *founder's*, who is the actual consumer of the display value and has no equivalent "deliberately don't trust this" signal.
