### PRODUCT / UX THINKER — Live-Surface CHALLENGE Findings

Scope: what a founder playing live 9-handed 1/2-1/3 on a Galaxy A22 actually sees, and whether the number/recommendation on screen is honestly backed by the computation it claims. Traced the path `useLiveActionAdvisor` → `computeHelpers.buildPostflopAdvice` → `gameTreeEvaluator.evaluateGameTree` → `LiveAdviceBar` / Ignition `render-street-card.js`, plus the recent WS-450/451/432 landings.

#### Key Concerns (top 5)

1. **The two-phase engine's fast path is unreachable in production — the live view still blocks on the full computation.** `evaluateGameTree` is built as two clocks precisely so the founder gets a depth-1 answer immediately and refinement happens in the background (`src/utils/exploitEngine/gameTreeEvaluator.js:1503-1526`, `onFastResult` param). But the sole production caller, `buildPostflopAdvice` (`src/utils/liveAdvisor/computeHelpers.js:251-272`), never passes `onFastResult`. `useLiveActionAdvisor` does one `await` and calls `setAdvice(assembledAdvice)` exactly once, only after the whole promise — fast **and** refined — resolves (`src/hooks/useLiveActionAdvisor.js:206-212, 357`). Every claim in `exploitEngine/CLAUDE.md`'s "Key Concepts" section about painting the fast answer while refinement continues is true of the engine and false of what the founder's phone shows. This was already named in `SYSTEM_MODEL.md` §2.3 ("no production caller wires `onFastResult` yet") — I confirmed it at the exact call site rather than taking the doc's word for it.

2. **The recompute-in-progress signal is dropped by its only consumer, so within-street advice can go silently stale.** `useAnalysisContext()` exposes `isComputing` (`src/contexts/OnlineAnalysisContext.jsx:57,72-82`), but the one place it's consumed, `CommandStrip.jsx:88`, destructures only `advice`. `LiveAdviceBar`'s staleness logic (`src/components/views/TableView/LiveAdviceBar.jsx:183-187`) is keyed on `currentStreet` mismatch and `adviceAge`, not on an in-flight-compute flag. A new bet/raise on the *same* street (villain check-raises the turn, say) triggers a fresh compute whose duration is bounded only by the refinement budget — during which the bar shows the pre-raise advice with no AGING/STALE badge and no spinner, because neither street nor 20s/60s age thresholds have been crossed yet.

3. **The "D2" depth pill on the Ignition sidebar collapses exactly the distinction the engine was built to preserve.** `depthReached` (`gameTreeEvaluator.js:1428`) is `depth3Ran ? 3 : depth2Ran ? 2 : 1` — a boolean "did any depth-2/3 stage start," not a completion signal. Each stage separately records `'completed'` vs `'partial'` plus a `weightConsumed` fraction (e.g. `gameTreeEvaluator.js:1671,1713,1782,1798,1851,1916`), and this file's own CLAUDE.md states the doctrine directly: *"`ran: true` at 3% and at 90% must never look the same again."* The only render site that surfaces this, `ignition-poker-tracker/side-panel/render-street-card.js:247-249` (`<span class="pill depth">D${tm.depthReached}</span>`), does exactly what the doctrine forbids. The main app's `LiveAdviceBar.jsx` is worse: it never reads `treeMetadata.latency` or `weightConsumed` at all (confirmed by grep — the only `treeMetadata.*` access is `advantage` at line 204), so depth-2/3 completion quality has zero surface in the app the founder actually plays from.

4. **WS-450/451's correctness fixes live in the phase least likely to finish on the founder's actual device, with no telemetry to know whether they did.** WS-451 (rake per-branch) is entirely inside `gameTreeDepth2.js`'s refinement stages; WS-450's depth-2/3 portion is too. Per this engine's own doctrine, "Full refinement measured up to 26s on a wet flop... at the 2000ms default most stages return marked partials" (`exploitEngine/CLAUDE.md` two-phase section), and `SYSTEM_MODEL.md` §10 lists "No performance metrics for game tree evaluation" as an open observability gap. WS-432 converted the budget from wall-clock to logical work-units calibrated against "a reference machine" (`gameTreeEvaluator.js:989-996`) — which removes *load*-dependence but does nothing to bound *wall-clock* time on a slower chipset; the target device (Galaxy A22 / Helio G80) has never been profiled against that reference (`SYSTEM_MODEL.md` A-07: "Game tree eval < 100ms on target device... RT-7 (physical device profiling) will validate" — still unresolved, and project memory independently tracks this same gap as open FIND-109). Net effect: two just-shipped domain-correctness fixes may frequently never execute on the phone during real play, and neither the founder nor this audit has a way to tell.

5. **Hand-plan / future-street guidance renders with the same visual confidence as the certified depth-1 numbers, despite being explicitly unvalidated.** `topRec.handPlan.ifCall?.note` and `ifRaise.plan` (`LiveAdviceBar.jsx:198-202,374-393`) come from depth-2/3 branches whose EV is flagged "not yet validated in production... under investigation — WS-361" (`exploitEngine/CLAUDE.md`) and which `holdingKnowledge` marks `basis: hypothesized` (never scoreable against a revealed hand, per the `holdingKnowledge/` System-Model entry). Visually it's a plain blue-on-dark text row, same weight class as the equity/fold%/EV row computed from the validated depth-1 path. Nothing on screen tells the founder "this multi-street plan is a projection the engine itself doesn't trust yet."

#### Hidden Risks

- **The advice object has no first-class hand identifier**, so every downstream staleness guard is reconstructing hand identity from proxies. `assembledAdvice` (`useLiveActionAdvisor.js:296-337`) carries `timestamp`/`currentStreet`/`villainSeat` but no `handNumber`. The Ignition side panel compensates by stamping `coordinator.get('currentLiveContext')?.handNumber` onto arriving advice *at receipt time* (`side-panel.js:566-577`, comment cites RT-45) — i.e. "whatever hand context happens to be cached right now," not the hand the advice was actually computed against. `pushAdvice`, `pushExploits`, and the live-context push each fire from independent React effects (`OnlineAnalysisContext.jsx:63-70`) with no cross-effect ordering guarantee, over a transport this repo's own docs describe as capable of queuing under burst load (`SYSTEM_MODEL.md` §7.2). A slow-resolving compute (see Concern #1/#3) that finishes after the live context has already advanced to the next hand gets stamped with the *new* hand's number and passes every guard clean. The main app's own `LiveAdviceBar` has no hand-identity check whatsoever — only street + age (`LiveAdviceBar.jsx:183-187`) — so this exposure exists in the primary surface, not just the extension.
- **Full recompute fires on every recorded opponent action, before it's even hero's turn**, and in-flight CPU work is never cancelled early — `isCurrent(callId)` is only checked *after* each async phase resolves (`useLiveActionAdvisor.js:253,267`), never before starting one. The hook explicitly computes "even if hero already acted — shows optimal play" (`useLiveActionAdvisor.js:104-108`). At a 9-handed table, a founder catching up by rapid-tapping several folds can trigger a burst of full, uncancellable postflop-game-tree computations that are each thrown away — competing for the same CPU budget as the one compute that will actually matter when it's his turn.
- **Preflop `heroAlreadyActed` advice is presented identically to actionable advice.** The bar doesn't visually distinguish "here's what you should have done" from "here's what to do now" — both render through the same `topRec` path with no state-specific framing, on a screen the founder is glancing at for under a second per SYSTEM_MODEL's stated live-use constraints.

#### Likely Missing Elements

- A visible "computing / refining" affordance tied to the actual in-flight state (`isComputing`) rather than inferred from street-mismatch or age thresholds that don't fire on within-street recomputes.
- A completion-quality signal (from `weightConsumed`/`latency` stage status, which the engine already computes) surfaced anywhere in either UI — currently thrown away between engine and both renderers.
- A carried `handNumber` on the advice payload itself, so downstream consumers verify hand identity against ground truth instead of reconstructing it from receipt-time context.
- A visual distinction between depth-1 (validated) and depth-2/3 hypothesized hand-plan guidance — even a single badge/opacity tier would honestly communicate WS-361's own stated confidence level.
- Device-calibrated telemetry for `REFINEMENT_UNITS_PER_MS` on the actual target hardware (Galaxy A22), so the logical-work-unit budget's real-world wall-clock behavior on the founder's phone is known rather than assumed.

#### Dangerous Assumptions

- **"The two-phase architecture means the founder always gets a fast answer."** False as shipped — the architecture exists in the engine; the only production caller awaits the whole thing synchronously. The founder gets exactly one answer, whenever the *slower* of the two phases finishes.
- **"`depthReached` tells you how good the depth-2/3 number is."** It tells you only whether the stage was attempted, not whether it got anywhere before the budget ran out — the file's own doctrine warns against this exact conflation and the UI does it anyway.
- **"Logical work-unit budgeting solved the mobile-latency problem."** It solved *reproducibility* (same inputs → same stage completion, any machine) — it did not bound or even measure wall-clock latency on the one device that matters, and this repo's own memory already tracks that measurement as outstanding (FIND-109).
- **"Street-rank + age is a sufficient staleness guard."** It catches cross-street contamination but not within-street recompute staleness (Concern #2) and not cross-hand contamination when timing coincidences align (Hidden Risk #1) — both are live-table-realistic scenarios, not edge cases requiring adversarial timing.
- **"A shipped correctness fix (WS-450/451) means the founder's advice is now correct."** True of the code path; unverified whether that code path executes to completion on his actual phone during his actual hands, given no performance telemetry exists for game-tree evaluation (`SYSTEM_MODEL.md` §10) and the refinement phase is documented as the one most likely to be cut short.
