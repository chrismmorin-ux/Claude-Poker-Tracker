**1. `handAnalysis/heroAnalysis.js` and `hindsightAnalysis.js` are an independent, unraked reimplementation of the exact formula WS-450 just fixed — and the fix's own CI gate cannot see it.**
`src/utils/handAnalysis/heroAnalysis.js:35,109` and `src/utils/handAnalysis/hindsightAnalysis.js:68,79` all compute `equityNeeded = betSize / (potSize + betSize)`. Tracing the caller (`replayAnalysis.js:485-489`, `potAtPoint` sums every prior timeline `amount` including villain's just-placed bet) confirms `potSize` here is "pot-includes-bet," so the formula is algebraically the correct caller's price — the same legitimate shape WS-450 annotated as `pot-includes-bet` at `actionClassifier.js:148`. It is *currently* correct, by accident of an undocumented convention, not by construction. Nothing marks it as the legitimate case, no comment states which pot convention is in force, and — more importantly — `scripts/check-required-equity-seam.mjs:21` only scans `src/utils/exploitEngine`, `src/utils/liveAdvisor`, `src/utils/rangeEngine`. `handAnalysis/` is invisible to the gate the founder just built specifically because this exact bug shipped five times. The next edit to this file (or a new hindsight-analysis file elsewhere) has no seam function to route through and no test that would catch the bluffer's-breakeven substitution landing here.

**2. Neither hindsight file threads rake at all.** `grep -rln "rake" src/utils/handAnalysis/` returns nothing. `computeCallEV = eq*(pot+bet)-bet` (`heroAnalysis.js:30`) has no `rakeConfig` parameter anywhere in the module. Post-WS-451, the live game-tree engine correctly rakes every called/showdown pot per branch (`gameTreeDepth2.js`, `potCalculator.rakedShowdownPot`). The hand-replay coaching view that tells the founder "you should have called" or "correct fold" for the *same real decision* computes it unraked. At live 1/2-1/3 stakes rake is a material fraction of small pots (SYSTEM_MODEL §6.2 names this exact cross-module risk: "Missing rake = systematically optimistic EV"), so the hindsight coach can rate a marginal call as "+EV, should have called" when the raked live engine — evaluating the identical spot — would call it -EV. This directly undercuts the founder's stated capability bar of trustworthy after-the-fact hand recreation.

Worse, the `ALLOW` regex (`line 23`) disables the check on ANY line containing the string `bluffer-breakeven`, `pot-includes-bet`, or `balanced-bluff-ratio` — nothing checks that the annotation is *true*. A wrong annotation silences the gate and reads, on review, as *more* trustworthy than an unannotated line, not less. This is the same "comment asserting something the code doesn't ensure" failure class the codebase's own CLAUDE.md flags repeatedly (WS-300's index-literal incident) — the remediation for one instance of that class reintroduces it.

#### Hidden Risks

- `heroActionBuilder.js:78-86` (MICRO/LOW SPR, no facing bet): emits `{ action: 'bet', betSize: effectiveStack, betFraction: effectiveStack/potSize }` unconditionally, including when `effectiveStack === 0`. A zero-size "bet" candidate is functionally a check but is labeled and reasoned about as an aggressive action; no filter drops degenerate-size candidates before they enter the EV pass.
- `multiwayFoldPct` (`gameTreeEquity.js:1110-1142`) multiplies per-opponent fold rates under a stated conditional-independence-of-hole-cards assumption; with up to 8 active opponents in a 9-handed game the product decays geometrically and is clamped to `[0.01, 0.95]` (`gameTreeEvaluator.js:665-668`) — the clamp hides how much of the tail is manufactured by the floor rather than measured, and the mean-field approximation (documented elsewhere as "strictly better than independence, strictly weaker than exact joint," POKER_THEORY §11.4) is not re-derived for the specific case of many simultaneous unknown opponents, which is exactly the founder's live 9-handed game.
- `villainRequiredEquity`'s raise branch (`foldEquityCalculator.js:382-396`) derives a "canonical" raise-to via `Math.min(B*3, P+B*2)` with **no `effectiveStack` parameter** — it cannot know hero is stack-capped. `heroActionBuilder.js` separately clamps candidate raise sizes to `effectiveStack`/`maxBet`. These two sizings are computed independently and can diverge for genuine short-stack all-ins, producing a required-equity number priced for a raise size hero cannot actually make.
- WS-451's per-branch rake in `computeDepth3BarrelEV` re-estimates rake independently on each of three chained pots (flop-call, turn-bet/check, river-bet/check) via `rakedShowdownPot`. For a rake structure with a flat dollar cap (common in low-stakes live cash), applying the cap logic independently per branch-pot rather than once on the final showdown pot is a materially different computation than what a real dealer does (rake is taken once, from the final pot); `rakePerBranch.test.js` per the commit description asserts exact-equality reconstruction and the §11.3 fold-branch invariance, but nothing in the diff indicates a capped/tiered rake config was exercised through the chained depth-3 path specifically.
